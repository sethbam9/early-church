# App Data Architecture

Canonical source-of-truth for the early-Christian history dataset and the derived tables used by the UI.

This document defines:

- what lives in canonical source tables
- what is derived and never hand-edited
- how sources, passages, claims, evidence, reviews, and notes fit together
- how to keep new AI insertion non-redundant and field-accurate

---

## Core principles

1. **Identity rows are minimal.**
   Entity tables store identity, labels, and editorial notes. Historical assertions belong in `claims.tsv`.
2. **Claims are atomic.**
   One row in `claims.tsv` expresses one assertion.
3. **Evidence is claim-specific.**
   `claim_evidence.tsv` does not restate the claim; it records how strongly one passage demonstrates that claim.
4. **Sources and passages are reusable.**
   Reuse existing `sources.tsv` and `passages.tsv` rows whenever possible. Do not create duplicate witness rows.
5. **Reviews are state + history.**
   `claim_reviews.tsv` stores the current review state. `claim_review_events.tsv` is append-only review history.
6. **Derived tables are regenerated only.**
   Never edit `data/derived/*.tsv` by hand.
7. **Change-based time ranges only.**
   Do not restate uninterrupted control/presence later just because time passed.
8. **Markdown references are part of integrity.**
   Links in markdown-capable TSV fields and scanned `.md` files must resolve.

## Source-of-truth boundaries

### Human-edited source tables

AI or humans may edit only:

- canonical entity tables
- `sources.tsv`
- `passages.tsv`
- `claims.tsv`
- `claim_evidence.tsv`
- `claim_reviews.tsv`
- `claim_review_events.tsv`
- `editor_notes.tsv`

### Never hand-edit derived tables

These are regenerated by validation:

- `derived_edges.tsv`
- `entity_place_footprints.tsv`
- `place_state_by_decade.tsv`
- `first_attestations.tsv`
- `proposition_place_presence.tsv`
- `note_mentions.tsv`

### One-row rule

Every source row must be exactly one of:

- identity
- assertion
- evidence mapping
- current review state
- review history event
- editorial commentary

Do not mix identity with historical summary, rollups, or derived state.

## Markdown and Bible reference rules

### Canonical wiki-link form

Use this exact shape in markdown-capable fields and scanned markdown files:

```text
\[\[type:id|Label\]\]
```

Examples:

- `\[\[person:paul|Paul\]\]`
- `\[\[work:first-epistle-of-clement|1 Clement\]\]`
- `\[\[place:jerusalem|Jerusalem\]\]`
- `\[\[group:roman-empire|Roman Empire\]\]`
- `\[\[bible:1Cor.11.23|1 Corinthians 11:23\]\]`

The label is optional. The ID is not.

### Bible references must use OSIS

Where a Bible reference is stored directly or linked through a `bible` wiki-link, the stored identifier must be OSIS.

Valid stored IDs:

- `John.3.16`
- `1Cor.11.23`
- `Gal.1.18-Gal.1.19`
- `1Cor.15.3-5`

Invalid stored IDs:

- `1 Corinthians 11:23`
- `1 Cor 11:23`
- `Gal 1:18-19`

In `passages.tsv`:

- `locator_type=bible_osis` → locator must be OSIS
- `locator_type=source_ref` → locator may use non-biblical systems such as `AH 3.3.2`, `Ant. 18.63-64`, `1QS 5.7-13`

## Entity tables

### `places.tsv`

Canonical place identity only.

| Column | Rules |
|---|---|
| `place_id` | Stable slug PK |
| `place_label` | Preferred historical/canonical label |
| `place_label_modern` | Preferred modern name when different |
| `place_kind` | Enum |
| `parent_place_id` | Optional containment FK |
| `lat` / `lon` | Optional coordinates |
| `location_precision` | Enum; required |
| `modern_country_label` | Display helper only |
| `notes` | Identity note only |

Do not store control, doctrine, planting traditions, first attestation, or period summaries here.

### `people.tsv`, `works.tsv`, `events.tsv`, `groups.tsv`

These follow the same rule: identity, labels, light editorial notes, no historical rollups.

Additional group rule:

- `group_kind=polity` is how political controllers are represented.
- Political control is modeled by `controls_place` claims, not by special polity tables.

### `topics.tsv`, `dimensions.tsv`, `propositions.tsv`

Use the proposition model for doctrinal content:

- `topic` = large domain
- `dimension` = axis inside that domain
- `proposition` = precise claimable position

The proposition row is neutral. Stance lives in the predicate, not in a second polarity field on claims.

## `sources.tsv` and `passages.tsv`

### `sources.tsv`

A source row is a **citable witness**, not necessarily the same thing as the canonical work identity.

Examples of valid source rows:

- an online edition of *Against Heresies*
- a journal article discussing a council
- a catalog record
- a later witness preserving fragments of a lost work

Key rule:

- `works.tsv` stores canonical work identity
- `sources.tsv` stores the citable manifestation/witness used for evidence

`source.work_id` is optional and should be populated when the source row directly represents that work.

### `passages.tsv`

A passage row is one reusable cited location inside one source.

| Column | Rules |
|---|---|
| `passage_id` | Stable slug PK |
| `source_id` | Required FK |
| `locator_type` | `bible_osis` or `source_ref` |
| `locator` | Required. OSIS only when `locator_type=bible_osis` |
| `excerpt` | Optional; short quote or labeled paraphrase |
| `language` | Optional |
| `passage_year` | Optional integer |
| `url_override` | Optional deep link |
| `notes` | Optional markdown note |

### Passage uniqueness rule

There should be **one canonical passage row per `source_id + locator_type + locator`**.

If two claims need different quoted slices from the same cited locator:

- keep one passage row
- put the claim-specific wording in `claim_evidence.excerpt_override`

Do not duplicate passage rows only because the excerpt wording differs.

### Excerpt form rule

If the excerpt is not verbatim, label it plainly at the beginning.

Recommended prefixes:

- `Paraphrase:`
- `Summary:`

Do not let a paraphrase silently overstate the source.

### Lost / fragmentary / testimonia rule

Some work claims are supported only through later witnesses.

Example pattern:

- target work = a lost or fragmentary work in `works.tsv`
- source = later author preserving/reporting it in `sources.tsv`
- passage = cited section in that later witness

This is valid, but it must be explicit.

Use the evidence note to mark the chain, for example:

```text
indirect_testimonium — later witness preserving/reporting the lost work
```

That marker tells the validator and future editors that a cross-work support row is intentional, not accidental duplication.

## `claims.tsv`

One row = one assertion.

| Column | Rules |
|---|---|
| `claim_id` | Stable slug PK |
| `subject_type` + `subject_id` | Canonical subject |
| `predicate_id` | Must match `predicate_types.tsv` |
| `object_mode` | Exactly one mode active |
| object/value field | Exactly one populated branch |
| `year_start` / `year_end` | Optional lower/upper bound |
| `context_place_id` | Optional contextual place |
| `certainty` | Historical confidence enum |
| `claim_status` | Lifecycle enum |
| `created_by` | Optional editor/importer id |
| `updated_at` | ISO date or RFC 3339 timestamp |

### Natural uniqueness target

No duplicate active claim should exist for the same logical assertion.

Normalize on:

- subject
- predicate
- object/value
- time window
- context place
- `claim_status=active`

### Status policy

Use status transitions instead of hard-deleting reviewed history whenever possible.

Recommended meanings:

- `active` — live canonical claim
- `draft` — incomplete insertion not ready for approval
- `superseded` — replaced by a stronger or merged claim
- `rejected` — unsupported / incorrect claim retained for audit history
- `deprecated` — retained for migration compatibility only

Hard deletion is acceptable only for obvious junk rows that were never legitimate canonical records.

### Change-based temporal rule

For uninterrupted states such as `controls_place` or `group_present_at`, store one continuous interval.

Correct:

- one row for uninterrupted Roman control of a place
- a new row only when control or presence changes, stops, or resumes after interruption

Incorrect:

- restating the same uninterrupted state at AD 100 and AD 350

### Redundancy rules

The canonical graph should avoid assertions that are already implied by better rows.

Key enforced/expected patterns:

- `bishop_of` makes overlapping `active_in` redundant for the same person/place
- `controls_place` makes overlapping `group_present_at` redundant for the same group/place
- `authored_by + written_at` often makes `active_in` unnecessary
- `participant_in + event_occurs_at` often makes `active_in` unnecessary
- `person_*_proposition` is redundant when all support comes from the person's own authored works and the corresponding `work_*_proposition` rows already exist

## `claim_evidence.tsv`

This table answers: **how does this specific passage relate to this specific claim?**

| Column | Rules |
|---|---|
| `claim_id` | FK → claims |
| `passage_id` | FK → passages |
| `evidence_role` | `supports`, `opposes`, `contextualizes`, `mentions` |
| `support_aspect` | Required when role=`supports`; otherwise normally blank |
| `assertion_mode` | Required when role=`supports`; otherwise normally blank |
| `excerpt_override` | Optional claim-specific slice/wording |
| `evidence_weight` | Optional decimal 0.0–1.0 |
| `notes` | Optional markdown note |

### Claim-evidence uniqueness rule

Use at most **one row per `claim_id + passage_id`**.

Do not create separate `supports` and `contextualizes` rows for the same claim/passage pair. Decide what that passage is doing for that claim and store one row.

### `evidence_role`

- `supports` — passage materially grounds the claim
- `opposes` — passage materially pushes against the claim
- `contextualizes` — useful background, not direct attestation
- `mentions` — only incidental mention

### `support_aspect`

Use only when `evidence_role=supports`.

Allowed values:

- `whole_claim`
- `subject`
- `predicate`
- `object`
- `date`
- `place`
- `context`
- `attribution`

Interpretation rule:

- `whole_claim` only when the cited text grounds the atomic assertion as a whole
- use `attribution` for claims that are about who reports/authors/attributes something
- use narrower aspects when the text supports only one component

### `assertion_mode`

Use only when `evidence_role=supports`.

Allowed values:

- `explicit`
- `strong_inference`
- `weak_inference`
- `background_only`

Rules:

- `supports + background_only` is invalid; use `contextualizes` instead
- `weak_inference` should normally include an explanatory note
- do not mark a claim `explicit` when the relation exists only by combining nearby material or broader context

### `evidence_weight`

Optional but recommended.

Suggested rubric:

- `0.95–1.00` — exact or near-exact direct support
- `0.80–0.90` — clear direct support with light compression/paraphrase
- `0.60–0.75` — real support but narrower or partly inferential
- `0.40–0.55` — indirect/testimonia/attribution support
- blank — unscored; acceptable during drafting, not ideal for mature rows

Use lower scores for:

- paraphrase-heavy evidence
- indirect testimonia
- narrower support aspects
- `weak_inference`

## Review model

### `claim_reviews.tsv`

One row per claim. This is the **current** review state.

| Column | Rules |
|---|---|
| `claim_id` | PK / FK |
| `reviewer_id` | Reviewer identifier |
| `review_status` | `unreviewed`, `reviewed`, `approved`, `disputed`, `needs_revision` |
| `reviewed_at` | ISO date or RFC 3339 timestamp |
| `confidence` | `low`, `medium`, `high` |
| `note` | Short rationale |

Rules:

- active claims should normally have one current review row
- do not create two current review rows for one claim
- update the existing review row instead

### `claim_review_events.tsv`

Append-only review history.

| Column | Rules |
|---|---|
| `claim_id` | FK |
| `event_type` | `created`, `reviewed`, `approved`, `disputed`, `reopened`, `needs_revision` |
| `actor_id` | Event actor |
| `event_at` | ISO date or RFC 3339 timestamp |
| `note` | Event note |

Rules:

- append, do not overwrite
- the latest event should normally match the current `claim_reviews.review_status`

---

## `editor_notes.tsv`

Editorial working notes, disputes, migration notes, and rationale.

Use this for:

- unresolved disputes
- reminders for future cleanup
- rationale that should not live in canonical claim fields
- markdown commentary with canonical links

Do not use it to replace missing claims or evidence.

## Derived tables

### `derived_edges.tsv`

Normalized direct and derived graph edges used for UI and rollups.

### `entity_place_footprints.tsv`

Map index for entity-place presence paths, including derived proposition footprints.

### `place_state_by_decade.tsv`

Decade rollup for map display. Repetition here is acceptable because it is a derived time-slice view.

### `first_attestations.tsv`

Computed earliest attestation per subject/predicate pair based on claims and linked passages.

### `proposition_place_presence.tsv`

Computed proposition stance by place and time.

### `note_mentions.tsv`

Parsed markdown references from TSV markdown-capable fields and scanned `.md` files.

## Validation behavior

The canonical validator is expected to enforce at least these classes of rules:

- schema/header correctness
- enums and foreign keys
- claim structure and one-branch object/value rules
- duplicate active claim detection
- change-based continuity for control/presence predicates
- passage natural uniqueness by `source + locator`
- evidence-row coherence
- review-table coherence
- markdown link integrity
- OSIS validation for Bible locators
- regeneration of derived tables

The validator may emit both:

- **errors** — must be fixed before merge
- **warnings** — strong cleanup guidance, especially for redundancy and evidence quality

---

## Practical insertion order

When adding new material, use this order:

1. reuse or create entity rows
2. reuse or create source row
3. reuse or create passage row
4. add claim row
5. add claim-evidence row
6. add or update current review row
7. append review event row
8. run validation

That order minimizes duplicates and keeps the graph coherent.
